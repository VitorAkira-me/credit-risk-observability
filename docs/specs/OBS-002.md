# OBS-002 · Métricas de saúde e alertas de drift no MLflow

- Etapa: 3
- Status: concluída
- Data: 08/11/2026
- Jira: [PMF4-20](https://akiravkax.atlassian.net/browse/PMF4-20)

## Objetivo
Um painel (UI do MLflow) em que dá para ver, semana a semana, se o pipeline e o modelo estão
saudáveis, com alertas que não disparam à toa. Atende a parte "métricas em dashboard ou MLflow"
da Etapa 3 e corrige as três réguas herdadas do DRIFT-002 (comentário no Jira).

## Conceito por trás (didático)
O log (OBS-001) conta cada execução; o MLflow empilha as execuções numa linha do tempo. Mas um
painel só ajuda se os alertas forem confiáveis. Uma régua calibrada para 9.000 linhas, aplicada a
2.000, alarma por acaso: é o "menino que gritava lobo", e depois de algumas semanas ninguém mais
olha. Por isso as réguas são calibradas em amostras **sem drift**, no mesmo tamanho do lote, e o
alarme falso é medido em amostras que a calibração não viu.

## Escopo
- Dentro:
  - `monitoring/alerts.py`: calibração (bootstrap da AUC e da taxa de default, KS com Bonferroni e
    D mínimo) e as quatro regras.
  - `monitoring/tracking.py`: um run do MLflow por execução, com params, métricas, tags e artefatos.
  - `scripts/calibrate_alerts.py`, `scripts/run_weekly_pipeline.py`, `scripts/plot_weekly_panel.py`.
  - 4 semanas de 2.000 clientes com drift crescente e 1 semana corrompida.
- Fora:
  - Prometheus/Grafana (`IMP-002`), retreino automático (`IMP-004`).
  - Minimizar o `failure_cases.csv` anexado (ADR-005, no GOV-001).
  - Mudar o destino padrão de `run_validation.py` e `make_drift_batch.py` (candidato a `IMP-*`).

## Critérios de aceite (verificáveis)
- [x] Um run do MLflow por execução, com a tag `pipeline_run_id` igual ao `run_id` do log (teste e execução real).
- [x] `log_param`: lote, semana, intensidade, versão do modelo, contrato, método de drift.
- [x] `log_metric`: latência por etapa, volume, linhas rejeitadas, nº de features com alerta, PSI por feature, AUC, taxa de default.
- [x] `log_artifact`: HTML do Evidently, eventos do log e `failure_cases.csv` na semana barrada.
- [x] Tag `drift_alert=true` quando alguma feature passa de PSI 0,25 (teste com 0,25 exato).
- [x] 4 semanas com drift crescente formando série temporal, mais uma barrada.
- [x] Alarme falso das réguas novas medido em holdout sem drift.
- [x] `uv run pytest -q` e `uv run ruff check .` limpos.

## Como validar de verdade
```
uv run python scripts/calibrate_alerts.py
uv run python scripts/run_weekly_pipeline.py
uv run python scripts/plot_weekly_panel.py
uv run mlflow ui --backend-store-uri sqlite:///mlflow.db
```

## Resultado
- Limites para n = 2.000: AUC ≥ 0,687; default entre 20,6% e 23,6%; KS com p < 0,0025 e D > 0,0;
  PSI > 0,25. Alarme falso no holdout: KS 1,5% (régua antiga: 24,5%), AUC 3,5%, default 7,0%.
- Semanas: 1 sem alerta (AUC 0,728); 2 com KS em `LIMIT_BAL` e `BILL_AMT1`; 3 com KS, AUC (0,685) e
  default (27,0%), PSI ainda 0,18; 4 com tudo, incluindo `drift_alert` (PSI 0,30 em `LIMIT_BAL`);
  5 barrada no contrato com 130 linhas rejeitadas.
- MLflow conferido por consulta: 5 runs, 33 métricas nas semanas aprovadas e 3 na barrada, artefatos
  presentes, `pipeline_run_id` batendo com o log de 9 linhas.
- 111 testes passando (12 novos em `tests/test_monitoring.py`).
- **Desvio:** o D mínimo do KS saiu 0,0, porque o Bonferroni sozinho já segura o alarme falso
  em n = 2.000. A condição fica no código para lotes maiores.
