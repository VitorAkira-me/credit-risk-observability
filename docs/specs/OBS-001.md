# OBS-001 · Logs estruturados em JSON para cada etapa do pipeline

- Etapa: 3
- Status: concluída
- Data: 08/11/2026
- Jira: [PMF4-19](https://akiravkax.atlassian.net/browse/PMF4-19)

## Objetivo
Toda execução do pipeline deixa um rastro consultável em `logs/pipeline.jsonl`: o que rodou, quanto
tempo levou, quantas linhas entraram e foram rejeitadas, e se deu certo. Atende a parte "logs do
pipeline (sucesso/falha, volume, latência)" da Etapa 3 e é a base do OBS-002 (MLflow).

## Conceito por trás (didático)
Log em texto é para humanos lerem; log estruturado (uma linha JSON por evento) é para máquinas
filtrarem e somarem. A diferença prática: com texto, "quantas validações falharam no mês?" exige
regex; com JSON é `status == "falha"` e uma contagem.

Analogia: o texto livre é um diário de bordo escrito à mão; o JSONL é a caixa-preta do avião, com
os mesmos campos em toda linha, pronta para ser lida por outra máquina.

Log, métrica e trace: o **log** conta o que aconteceu num evento (por que a validação de terça
falhou); a **métrica** é um número agregado no tempo (quantas falharam no mês); o **trace** segue
uma requisição por vários serviços. Aqui o `run_id` faz um papel de trace simples: liga os eventos
de uma mesma execução.

## Escopo
- Dentro:
  - Esquema fixo em todo evento: `timestamp, run_id, etapa, evento, status, duracao_s,
    linhas_entrada, linhas_rejeitadas, detalhe` (os 8 campos do card + `evento`, o nome da
    ocorrência, que os testes e o OBS-002 usam para filtrar).
  - `pipeline_step`: context manager que mede a duração e grava `status=falha` também quando o

  - Rotação de log e retenção (vai para o GOV-002 como política, não código).
  - `prepare_data.py` e `train_baseline.py` sem log estruturado (candidatos a `IMP-*`).

## Como validar de verdade
```
uv run python scripts/run_validation.py data/production/production_base.parquet     # exit 0
uv run python scripts/run_validation.py data/production/batch_corrupted.parquet     # exit 1
tail -n 2 logs/pipeline.jsonl
```
Esperado: duas linhas, uma `sucesso` com 9.000 linhas de entrada e 0 rejeitadas, e uma `falha` com
as linhas rejeitadas contadas e as regras em `detalhe.falhas_por_regra`.

## Riscos e perguntas em aberto
- `linhas_rejeitadas` conta linhas distintas com pelo menos uma falha. Falhas do lote inteiro
  (coluna faltando, tipo errado) não têm linha: nesse caso o lote todo é rejeitado.
- Pergunta para o Akira: um lote com 1 linha ruim em 9.000 deveria ser bloqueado inteiro, ou só a
  linha ir para quarentena? (hoje: bloqueado inteiro; quarentena é o `IMP-005`).
