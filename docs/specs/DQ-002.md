# DQ-002 · Lote corrompido bloqueado na ingestão

- Etapa: 1 (requisito: lote com erros falhando e sendo bloqueado)
- Status: concluída
- Data: 21/10/2026

## Objetivo
Provar que o contrato do DQ-001 funciona como **portão**: um lote com defeitos conhecidos é
barrado com exit code 1, log estruturado e relatório das falhas; um lote limpo passa com exit 0.

## Conceito por trás (didático)
Um contrato que só existe em teste não protege nada. Ele precisa estar **no caminho** dos dados,
com um sinal que a automação entenda. Esse sinal é o *exit code*: 0 diz "pode seguir", qualquer
outro número diz "pare". Airflow, GitHub Actions e o `&&` do shell leem esse número para decidir
se executam o próximo passo. O teste de verdade é saber a resposta antes: injetamos defeitos
**contados**, e a validação tem que achar **exatamente** esses números. Se achar a mais ou a
menos, há bug no contrato ou no gerador.

## Escopo
- Dentro: gerador `scripts/make_corrupted_batch.py`, portão `scripts/run_validation.py`, log
  JSON em `logs/pipeline.jsonl` (base para o OBS-001), relatório em `reports/validation/`.
- Fora: quarentena de linhas ruins deixando o resto passar (IMP-QUARENTENA).

## Defeitos injetados (seed 42, 1.000 linhas amostradas da Produção-base)
| Defeito | Linhas | Regra esperada | Falhas esperadas |
|---|---|---|---|
| `AGE = 15` | 50 | `AGE:in_range(18, 100)` | 50 |
| `LIMIT_BAL` nulo | 30 | `LIMIT_BAL:not_nullable` e `LIMIT_BAL:dtype('int64')` | 30 + 30 |
| `SEX = 3` | 10 | `SEX:isin([1, 2])` | 10 |
| Linha duplicada (mesmo ID) | +20 | `ID:field_uniqueness` | 40 (original e cópia) |

Cada defeito cai em linhas diferentes dos outros, para as contagens não se misturarem.

## Critérios de aceite (verificáveis)
- [x] Lote corrompido: exit code 1, evento `validation_failed`, contagens idênticas às esperadas
- [x] Lote limpo (Produção-base): exit code 0, evento `validation_passed`
- [x] `failure_cases` salvo em `reports/validation/`
- [x] `&&` no shell não executa o passo seguinte quando o lote falha
- [x] Exit codes iguais no Git Bash e no PowerShell
- [x] Testes do portão passam (31 no total)

## Como validar de verdade
```
uv run python scripts/make_corrupted_batch.py
uv run python scripts/run_validation.py data/production/production_base.parquet ; echo $?   # 0
uv run python scripts/run_validation.py data/production/batch_corrupted.parquet ; echo $?   # 1
```
No PowerShell, troque `echo $?` por `$LASTEXITCODE`.

## Resultado (preencher ao concluir)
- Lote corrompido (1.020 linhas): 5 regras violadas, `{AGE: 50, ID: 40, LIMIT_BAL dtype: 30,
  LIMIT_BAL nulo: 30, SEX: 10}`, **idêntico ao esperado**; 160 linhas em `failure_cases`; exit 1.
- Produção-base (9.000 linhas): aprovada em ~80 ms, exit 0.
- **Erro de previsão:** eu esperava 1 falha de tipo em `LIMIT_BAL`; vieram 30. Investigado: sem
  nulos, uma coluna float gera 1 falha (coluna inteira); com nulos, o Pandera atribui a falha de
  tipo a cada linha nula. O contrato estava certo, a expectativa estava errada.
- Atenção para a Etapa 4: `failure_cases` guarda valores reais das linhas barradas (ID, idade).
  Em produção isso é dado pessoal e precisa de política de retenção.
