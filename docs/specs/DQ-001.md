# DQ-001 · Contrato de dados com regras rígidas

- Etapa: 1 (requisito: contrato com ≥ 3 regras rígidas)
- Status: concluída
- Data: 21/10/2026

## Objetivo
Definir em código (Pandera) o formato que todo lote precisa ter para chegar ao modelo, com
testes que provam que cada regra barra o seu defeito e que os dados legítimos passam. O
bloqueio da ingestão com lote corrompido é o DQ-002.

## Conceito por trás (didático)
O contrato é o segurança na porta: confere a lista antes de deixar entrar. Ele barra o
**impossível ou ilegível** (idade 15, limite nulo, ID repetido, coluna faltando). Ele **não**
barra o **diferente mas possível** (clientes mais jovens, faturas maiores): isso é drift, e
quem cuida é o Evidently na Etapa 2. Misturar os dois papéis tem custo: um contrato apertado
demais rejeita clientes reais; um frouxo demais deixa lixo chegar ao modelo, que responde com
confiança mesmo assim.

## Regras (schema `credit_default_input_v1`)
| # | Regra | Por quê |
|---|---|---|
| 1 | Colunas exatas: nenhuma faltando, nenhuma extra (`strict=True`) | coluna nova pode ser PII vazando (ex.: CPF); faltando, o modelo quebra |
| 2 | Tipos `int64` sem coerção, sem nulos | `coerce=False`: float no lugar de int é sintoma de nulo ou de bug a montante |
| 3 | `ID` único e > 0 | um cliente por linha; duplicata dobra o peso do cliente nas métricas |
| 4 | `AGE` entre 18 e 100 | idade mínima legal para contratar crédito |
| 5 | `LIMIT_BAL` > 0 | limite zero ou negativo não existe |
| 6 | `SEX` em {1, 2}; `EDUCATION` em 0..6; `MARRIAGE` em 0..3; `PAY_*` em -2..9 | domínio dos códigos, **incluindo os legados** da Referência |
| 7 | `PAY_AMT*` ≥ 0 | valor pago negativo não existe |
| 8 | `default` em {0, 1}, **opcional** | lote de escoragem chega sem alvo |
| 9 | Lote não vazio | lote vazio passaria em todas as regras de coluna: sucesso vazio |

## Decisões
- **Aceitar códigos legados** (EDUCATION 0/5/6, MARRIAGE 0, PAY -2/0): existem nos 30k reais
  (≈ 1% em EDUCATION). Barrar rejeitaria clientes que o modelo foi treinado para atender.
- **Sem regra de faixa em `BILL_AMT`:** 1.930 clientes têm fatura negativa (crédito a favor).
- **Unicidade por `ID`, não por linha inteira:** das 70 linhas "idênticas ignorando ID", 60
  têm todas as faturas zeradas (cartões inativos com perfil igual). São clientes diferentes.
- **`lazy=True`:** coleta todas as violações de uma vez; vira relatório no DQ-002.

## Critérios de aceite (verificáveis)
- [x] ≥ 3 regras rígidas (são 9)
- [x] Cada regra tem um teste que a viola isoladamente e falha com a contagem certa
- [x] Raw, Referência e Produção-base reais passam sem nenhuma falha
- [x] Todas as violações aparecem num único relatório (`lazy=True`)
- [x] `uv run pytest -q` passa; ruff limpo

## Como validar de verdade
```
uv run pytest tests/test_contract.py -v
uv run python -c "import pandas as pd; from credit_risk_observability.contracts.validate import validate_batch; r=validate_batch(pd.read_parquet('data/reference/reference.parquet')); print(r.passed, r.rows, r.failures_by_rule)"
```

## Resultado (preencher ao concluir)
- Raw 30.000, Referência 21.000, Produção-base 9.000: `passed=True`, 0 falhas.
- 14 testes de contrato (28 no total), um por regra, mais lote limpo, lote sem alvo e
  "todos os erros de uma vez".
- **Armadilha pega no teste:** sem a regra 9, um DataFrame vazio passava no contrato.
- Detalhe da API: falhas do lote inteiro vêm com o nome do schema no campo `column`; o
  resumo usa `schema_context` para rotulá-las como `<lote>`.
- Pandera 0.34.1 fixado.
