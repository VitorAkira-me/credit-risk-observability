# ML-001 · Modelo baseline treinado na Referência

- Etapa: 1 (requisito "modelo baseline")
- Status: concluída
- Data: 21/10/2026

## Objetivo
Treinar um modelo simples de credit scoring **só com a Referência**, salvar o artefato e as
métricas em JSON. Ele é o "modelo em produção" cuja degradação vamos detectar no DRIFT-002.

## Conceito por trás (didático)
O baseline não precisa ser o melhor modelo, precisa ser **honesto e medido**. É a régua: sem
saber quanto ele acerta hoje, não há como dizer que piorou amanhã. Por isso medimos em três
lugares: treino (o que ele decorou), validação (dados da Referência que não viu) e Produção sem
drift (o grupo de controle). Se validação e Produção-base já diferem, essa diferença é o **ruído
natural**, e o drift só "dói" de verdade quando passa desse ruído.

## Escopo
- Dentro: Pipeline sklearn (OneHot + StandardScaler + LogisticRegression balanceada), split
  80/20 da Referência, métricas AUC, KS, recall/precisão/F1 da classe default, Brier,
  `models/baseline_metrics.json` versionado, modelo `.joblib` regerável (fora do git).
- Fora: tuning, outros algoritmos, calibração de probabilidade, escolha de limiar ótimo (IMP).

## Decisões
- **LogisticRegression:** explicável (coeficientes), rápida, padrão em crédito. Facilita a
  explicação exigida pelo art. 20 da LGPD.
- **Pré-processamento dentro do Pipeline:** o scaler aprende só no treino; o mesmo objeto
  transforma a Produção. Fazer o scaling "por fora" antes do split seria vazamento.
- **`class_weight="balanced"`:** com 22% de default, sem peso o modelo prioriza dizer "paga".
  Custo: probabilidades descalibradas (Brier ~0,20); aceitável para um baseline de ranking.
- **ADR-004:** `SEX` e `MARRIAGE` fora das features, mantidos nos dados para auditar viés.
- **`EDUCATION` raro (< 1%)** agrupado como "infrequente"; código desconhecido não quebra a predição.

## Critérios de aceite (verificáveis)
- [x] Treino usa só `data/reference/` (Produção nunca entra no `fit`)
- [x] `models/baseline_metrics.json` com métricas de treino, validação e Produção-base
- [x] AUC de validação > 0,70
- [x] JSON registra versões (Python, scikit-learn), features e hash do raw
- [x] `uv run pytest -q` passa; ruff limpo

## Como validar de verdade
```
uv run python scripts/train_baseline.py
uv run python -c "import json; m=json.load(open('models/baseline_metrics.json', encoding='utf-8'))['metrics']; print({k: v['roc_auc'] for k, v in m.items()})"
```

## Resultado (preencher ao concluir)
| Conjunto | Linhas | AUC | KS | Recall default | Precisão default |
|---|---|---|---|---|---|
| Treino | 16.800 | 0,7277 | 0,383 | 0,650 | 0,380 |
| Validação | 4.200 | 0,7318 | 0,384 | 0,657 | 0,384 |
| Produção-base | 9.000 | 0,7149 | 0,365 | 0,640 | 0,368 |

- Treino e validação próximos: sem overfitting.
- **Achado:** a AUC de validação varia de 0,714 a 0,732 só trocando a seed do split (seeds 1 a 5);
  a da Produção-base fica estável em ~0,715 (IC 95% bootstrap: 0,702 a 0,728). A seed 42 caiu num
  split de validação favorável. **Desempenho real do baseline: ~0,715.**
- Consequência para o DRIFT-002: comparar Produção com drift contra a **Produção-base**, não contra
  a validação, e considerar queda relevante só fora do IC acima.
